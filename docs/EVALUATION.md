# A/B 对照实验：本工具流程 vs 直接把论文交给模型

> ## ⚠️ 旧数字（145/113 : 7）**已作废，不能用于证明优势**
> 旧结果是在**层层截断**的评估链路上得到的：`benchmark.mjs` 每页只取前 1400 字符、
> `index.mjs` 每条证据截 400 字符且最多 30 条、`llm.mjs` 每条最终只取 320 字符。
> 实测旧"全文证据池"只覆盖正文 **34.9%**，**35 页中 33 页有内容被丢弃**（`docs/results/scope-local.md`）。
> 所以旧数字里的"无依据"很大一部分是**评估链路自己丢掉了证据**，不能读成"模型没有依据"。
>
> 同口径重评脚本已就位（两臂同样切分主张、同一检索与复核标准、公开分母与未复核数），
> 但**本轮判定未能跑完**：本会话没有可用的模型凭据（`/api/health` 的 `realLlmQa=false`），
> 判定结果全部落到「未复核」，据此**不给出任何 A/B 优劣结论**。
> **重评状态：未完成** —— 凭据可用时执行 `BENCH_LIVE=1 node scripts/benchmark.mjs`（复用缓存答案，只跑判定）。

> 本文其余数字来自**实际运行**：`node scripts/benchmark.mjs`（`BENCH_LIVE=1`）。
> 原始数据：`docs/results/benchmark.json`、`docs/results/benchmark.csv`；复现命令见文末。
> **没有为了结果好看修改人工标准答案**；相反，按原文核对后**修正过 4 处标准答案**（其中一处是工具发现的）。修正记录见第 5 节。

## 1. 实验设置

| 项目 | 内容 |
| --- | --- |
| 论文 | DLinear（15 页）、Autoformer（20 页），均为文本型 PDF，逐页解析后缓存 |
| 模型 | 两臂使用**同一个模型、同一个网关**（`claude-sonnet-4-20250514`） |
| A 臂（基线） | 「直接把论文正文交给模型提问」：`/api/bench/raw-ask`，无引用校验、无结论支持判定、无规则推导上下文，回答里自己写页码 |
| B 臂（本工具） | 真实 PDF 按页解析 → 字段抽取 + **引用逐字校验** + **原文支持判定** → 本地确定性规则检查 → 带引用校验与结论复核的问答 |
| 判定口径 | A 臂的每条结论也用**同一套支持判定**过一遍，证据池是 B 臂抽到并通过逐字校验的原文片段（保证两臂被同一把尺子量） |
| 案例数 | 6 个（每类人工标准答案：风险项清单 + 不允许出现的说法 + 是否应当拒答） |

案例覆盖四类场景：

| 案例 | 类别 | 问题 |
| --- | --- | --- |
| case-1 | 数据集集合不同但共同实验一致 | 两篇实验结果能直接比较吗？什么条件下可以比较？ |
| case-2 | 同一数据集上的实验条件不同 | ETTm1 / Traffic 上采样间隔一样吗？ |
| case-3 | 关键信息未找到 | 复现 DLinear 训练过程，哪些关键设置论文没给出？ |
| case-4 | 关键信息未找到（应拒答） | 两篇的随机种子分别是多少？ |
| case-5 | 引用真实但不支持结论（错误前提） | 「DLinear 所有数据集都是 5 分钟采样」这个说法对吗？ |
| case-6 | 关键信息未找到（应拒答） | Autoformer 用了多少块 GPU、训练多久？ |


## 2. 总体结果（6 个案例，第 3 轮重评后的实际数字）

> 第 3 轮做了两件事：① 用**同样的全文证据范围**（把两篇论文每一页正文都作为可用依据）重新判定 A 臂，
> 同时保留"只用工具抽到的片段"这一窄口径，两个数字都公开；② 修正了人工标准答案里的错误（见第 5 节），
> 并对两臂统一重新评分。

| 指标 | A 臂：裸模型 | B 臂：本工具 | 说明 |
| --- | --- | --- | --- |
| 风险项召回率 | 94.4%（17/18） | **100%（18/18）** | A 只漏了 case-1 的「数据集集合不同」 |
| 无依据结论（窄口径：只用工具校验片段当依据） | **145** | **7** | 这一列会高估 A，见下行 |
| 无依据结论（**全文口径**：每一页正文都算依据） | **113** | **7** | 放宽证据范围后 A 下降约 22%，差距依然很大 |
| 未复核（判定失败） | 24 / 26 | 0 | A 的长回答（case-3 有 75 句）分批复核更容易失败 |
| 误报（说了不该说的） | **1** | **1** | 两臂都命中 case-5 的 `mustNotAssert` |
| 正确拒答 | **3/3** | **3/3** | 三个"信息未给出"的案例都明确说明没给 |
| 结构化信号成立数 | — | **14/14** | 与人工标注的期望判定**全部一致**（第 2 轮曾 3 项不一致，见第 5 节） |
| 每条风险项的证据页码 | 有，但**未校验** | 有，**逐字校验后可跳转** | A 实测会把两篇的页码混写在同一句里 |

逐案例明细（A 的无依据数同时给窄口径 / 全文口径）：

| 案例 | A 句数 | A 无依据（窄 / 全文） | A 召回 | B 结构化信号 | B 召回 | B 无依据 |
| --- | --- | --- | --- | --- | --- | --- |
| case-1 | 59 | 26 / 20 | 67% | 3/3 | 100% | 3 |
| case-2 | 26 | 19 / 7 | 100% | 2/2 | 100% | 0 |
| case-3 | 75 | 53 / 42 | 100% | 5/5 | 100% | 3 |
| case-4 | 9 | 7 / 4 | 100% | 1/1 | 100% | 1 |
| case-5 | 42 | 16 / 10 | 100% | 2/2 | 100% | 0 |
| case-6 | 15 | 13 / 13 | 100% | 1/1 | 100% | 0 |

> 复现方式：`BENCH_LIVE=1 BENCH_REFRESH=1 node scripts/benchmark.mjs`（全量重跑，约 25 分钟）；
> 答案会缓存到 `benchmark/cache/answers-*.json`，之后 `BENCH_LIVE=1 node scripts/benchmark.mjs`
> 只重跑判定步骤；`node scripts/bench-patch.mjs` 用于定点补跑与用修正后的标准答案统一重评。

## 3. 结论（不预设工具更好）

1. **"有没有发现风险"这件事上差距很小**：A 94.4%，B 100%。这个模型本身足够强，
   **光看召回率不能说明工具的价值**。
2. **差距集中在"每条结论是否真有依据"**：即使把证据范围放宽到全文，A 仍有 113 条结论无法在原文里找到支持，
   B 是 7 条。A 的典型问题是把两篇的表格数字混在一起、给出论文未写明的训练细节。
3. **拒答能力两臂持平（3/3）**：对这个模型来说"论文没写"它会说清楚；
   工具的价值在于把拒答变成**可核验的状态**（未找到 / 未检查 / 未复核 各有界面与页码）。
4. **B 的低无依据数是设计出来的**：每条风险项都带页码与原文片段，比较结论由本地规则给出并带规则编号。
5. **两臂各有 1 条误报**（case-5 命中「DLinear 所有数据集都是 5 分钟采样」）。
   **本工具并没有消除误报**，只是把误报限制在可核对引用的范围内。
6. **B 的结构化信号 14/14 全对**：这是本轮修复的直接结果 —— 第 2 轮有 3 项不一致，
   查清后发现是**工具的 2 个真实缺陷 + 我的 1 处标准答案错误**（见第 5 节）。
7. **工具反过来纠正了人工标注**：case-6 我原以为论文没写 GPU 数量，工具的带引用答案给出
   「单块 NVIDIA TITAN RTX 24GB」（来自实现细节），核对原文后确认工具是对的。

## 4. 指标口径与已知偏差（必须一起看）

- **A 臂的"无依据"高度依赖证据池大小**：窄口径 145 → 全文口径 113。两个数字都保留、都公开，
  就是为了避免用窄口径制造虚高优势。但即使取全文口径，**也不能把 145:7 或 113:7 当成结论**。
- **A 臂的结论按句切分**（≥12 字），一句可能含多个事实；B 臂的结论来自受控生成，粒度更粗。
- **A 臂的页码未校验**：表中"A 证据页"只是从文本里抽出的页码标记，实测出现过把两篇页码混写的情况。
- **生成与判定是同一个模型**：存在同类偏见，所以单看支持判定不足以证明工具更好。
- **样本量只有 6 个案例、2 篇论文**：只能作为定性对照，不做统计推断。
- **未复核**（判定失败）A 臂有 24~26 条，已如实计入分母，没有剔除。

## 4b. 评估链路修正（本轮新增，含链路验证）

**问题**（用户核对代码时发现）：所谓"全文证据"其实被截断三次，页面中后部的证据整体丢失：

| 位置 | 旧行为 | 现行为 |
| --- | --- | --- |
| `scripts/benchmark.mjs` | 每页只取前 **1400** 字符 | 每页切成 **1600** 字符的块，**不丢内容**（`full-<paper>-p<page>-<i>of<n>`） |
| `server/index.mjs` | 每条证据截 **400** 字符、最多 **30** 条 | 每条 **4000** 字符、最多 **200** 条 |
| `server/llm.mjs` | 每条证据最终只取 **320** 字符 | 每条 **2400** 字符 |

**链路验证（证据位于页面中后部）**：`node scripts/probe-tail-evidence.mjs` 从 DLinear 第 1 页
约 2.9k 字符处取一句真实原文，构造对应主张，分别用两套池判定（日志：`docs/results/tail-evidence-probe.log`）：

| 证据池 | 该句在池中 | 判定结果 |
| --- | --- | --- |
| 旧（每页前 1400 字） | **不存在** | `support=none`（"片段池中没有出现该引文表述"） |
| 新（全文分块） | 存在 | **`support=full`**，命中 `full-dlinear-p1-2of3` |

**覆盖率量化（模型无关）**：正文总 136,540 字符 → 旧池 47,695 字符（**34.9%**）／新池 136,644 字符（**100%**）；
35 页中 **33 页**有内容被丢（`docs/results/scope-local.md`）。

**"未检索到支持" ≠ "原文不存在支持"**：界面与报告都把两件事分开 ——
检索不到只是检索层信号；本工具在问答里用「未复核」表示判定失败，用「未找到」表示**全部页面都处理过**后仍未读到。
A/B 重评也按此原则报告：**分母（判定成功的句数）、无依据比例、未复核数量三者同时给出**，
内部撤回（B 的 `withdrawn`）单独统计，不混进"展示文本"的比例。

## 5. 标准答案修正记录 + 由它暴露出的工具缺陷（全部保留）

| 轮次 | 案例 | 发现的问题 | 处理 |
| --- | --- | --- | --- |
| 第 1 轮 | 原 case-2（划分比较） | 假设「DLinear 7:1:2 vs Autoformer 6:2:2 → 存在差异」**不成立**：逐页检索确认 **DLinear 全文没有写划分比例**（只说 following the experimental setting of previous work） | 该案例改为比较**采样间隔**；「划分比例未写明」补进 case-3 风险项 |
| 第 1 轮 | case-5 | 假设「DLinear 的 ETTm 都是 15 分钟」**不完全对**：论文**表 1 把 ETTm 粒度写作 5 min**，与 15 分钟说法矛盾 | 标准答案改为「采样间隔不是统一值，且论文内部自相矛盾，需要确认」 |
| 第 2 轮 | case-1 | 期望「整体口径下跨度一致」是**错的**：Autoformer 的跨度集合多出 COVID-19 的 {7,15,30} 与 ETT 完整基准跨度 | toolSignal 改为期望 `different`；风险项改为「指标一致，但整体口径下跨度不一致」 |
| 第 2 轮 | case-6 | 以为「论文没给 GPU 数量」是**错的**：实现细节写了「单块 NVIDIA TITAN RTX 24GB」（**由工具找到，人工漏了**） | 拆成两条：GPU 数量有写（必须答出）、训练总时长没写（必须拒答） |

同时修掉的**工具侧真实缺陷**（由这 3 个信号不一致暴露出来，已加回归测试）：

| 缺陷 | 表现 | 修复 |
| --- | --- | --- |
| 「主实验 / 主设置」这类统一表述没被当作通用子句 | Autoformer 写「多变量主实验 O ∈ {96,192,336,720}」，限定到 Traffic / ETTm1 时被判成"论文没说明"→ 信息不足 | `GENERAL_CLAUSE` 增加「主实验 / 主要实验 / 主设置 / 多数数据集 / main experiments」等表述 |
| 数据集名里的括号没被拆开 | `ETT（ETTh1、ETTh2…）` 被拆成 `ETT（ETTh1`，导致 ETTh1 在第二篇里匹配不上、相关项误判信息不足 | `rawDatasetsOf` 把中英文括号也当分隔符（并加回归测试） |

## 6. 仍未解决的问题（明确标注）

1. **判定对证据池大小敏感**：同一批答案换证据池会让"无依据"数变化 20% 以上。
   更稳的做法是"先检索再判定"（先在全文里定位相关段落，再判断支持与否）。**未做。**
2. **生成与判定是同一个模型**：更严格的做法是用另一个模型或人工做判定。**未做。**
3. **案例数只有 6 个**：需要再引入 1~2 篇论文覆盖更多"引用真实但不支持结论"的形态。**未做。**
4. **A 臂长回答容易复核失败**（case-3 有 18 条未复核）：需要更好的分批与重试策略。**未做。**
5. **首次抽取质量会传导到结论**：DLinear 的 `split` / `sampleInterval` 抽取质量曾直接压低 B 的召回；
   放大 token 预算（思考型模型会耗尽预算导致空返回）后重抽才正常。这类传导需要单独统计。**未做。**

## 7. 复现命令

```bash
# 1. 启动后端（需要 LLM_API_KEY）
npm run build && node server/index.mjs

# 2. 缓存两篇论文的解析与抽取结果（每篇约 80 秒；PDF 需自备）
node scripts/extract-one.mjs testpapers/DLinear-Are-Transformers-Effective.pdf benchmark/cache/dlinear.json
node scripts/extract-one.mjs testpapers/Autoformer.pdf benchmark/cache/autoformer.json

# 3. 全量跑对照实验（约 25 分钟，真实调用模型）
BENCH_LIVE=1 BENCH_REFRESH=1 node scripts/benchmark.mjs

# 4. 只重跑判定（复用已缓存答案，不重新提问）
BENCH_LIVE=1 node scripts/benchmark.mjs

# 5. 定点补跑 + 用修正后的标准答案统一重评
node scripts/bench-patch.mjs

# 6. 只看工具侧的结构化判定（不调用模型，秒级）
node scripts/probe-scope.mjs
```

> `testpapers/` 与 `benchmark/cache/` 已被 `.gitignore` 排除：前者是论文原文 PDF，后者是逐页正文缓存，
> 都涉及版权，不入库。因此**复现时请自备这两篇 PDF**（arXiv 公开版本即可）。
